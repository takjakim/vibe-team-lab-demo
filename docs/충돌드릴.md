# 충돌 드릴 진행안 (강사용)

팀원 모두가 `src/data/team.json` 배열 끝에 자기 카드를 추가하는 동안, 강사가 같은 위치에 카드를 먼저 병합해 의도적으로 충돌을 만든다. 학습자는 충돌 확인, 해결, 검사, 강제 푸시(with lease)를 한 번씩 경험한다. 소요 시간은 약 30분이다.

## 준비

| 항목 | 확인 방법 |
|---|---|
| 드릴 이슈가 있다 | `gh issue list --label drill --repo <팀저장소>` |
| 강사가 저장소 관리자다 | 저장소 Settings 메뉴가 보인다 |
| 섹션 PR이 모두 병합되었다 | `gh pr list --repo <팀저장소>`가 비어 있다 |
| 강사 PC에 gh, node가 있다 | `gh auth status`, `node --version` |

main 보호 규칙은 관리자 우회를 허용한다(`enforce_admins: false`). 그래서 강사는 드릴 스크립트로 main에 바로 푸시할 수 있다.

## 진행 순서

| 단계 | 강사 | 학습자 | 예상 결과 |
|---|---|---|---|
| 1 | 드릴 이슈를 화면에 띄우고 목표를 설명한다 | 이슈 내용을 읽는다 | |
| 2 | 카드 추가 PR을 만들되 병합하지 말라고 안내한다 | 실습 가이드 4-1대로 PR 생성(`Refs #6`) | PR 4~5개가 열리고 check 통과 |
| 3 | `scripts/conflict-drill.sh <팀저장소>` 실행 | 대기 | main에 "강사 (충돌 드릴)" 카드 추가 |
| 4 | PR 목록 화면을 띄운다 | 자기 PR 확인 | 모든 PR에 "This branch has conflicts" |
| 5 | 리베이스 명령을 안내한다 | `git fetch origin && git rebase origin/main` | `CONFLICT (content): Merge conflict in src/data/team.json` |
| 6 | 충돌 모양을 함께 읽는다 | 충돌 파일 열기 | 아래 "충돌 모양" 참고 |
| 7 | 두 카드를 모두 남기라고 안내한다 | 해결 후 `node scripts/check.mjs` | 검사 통과 |
| 8 | `--force-with-lease`의 의미를 설명한다 | `git add`, `rebase --continue`, `git push --force-with-lease` | PR의 충돌 표시가 사라지고 check 재실행 |
| 9 | 병합 순서를 정해 한 명씩 병합시킨다 | 차례가 되면 승인 받고 병합 | 뒷사람 PR에 다시 충돌이 생긴다 |
| 10 | 5~8을 반복시키고 마지막에 드릴 이슈를 닫는다 | 반복 | main의 team.json에 전원 카드 |

스크립트 사용법은 다음과 같다.

```bash
scripts/conflict-drill.sh <팀저장소>                       # 기본 github 값 drill-instructor
DRILL_GITHUB=drill-2 scripts/conflict-drill.sh <팀저장소>  # 같은 저장소에서 두 번째로 진행할 때
```

스크립트는 임시 폴더에 새로 복제해서 작업하므로 강사의 작업 폴더는 바뀌지 않는다. main 직접 푸시가 막히면 임시 브랜치와 PR을 만들고 관리자 권한 병합(`gh pr merge --squash --admin`)을 시도하며, 그것도 실패하면 수동 병합 명령을 출력한다.

## 충돌 모양

Git은 두 카드의 공통 줄인 `{`와 `}`를 하나로 맞춰 버리기 때문에, 충돌 표시가 카드 한 개 안쪽에 생긴다. 학습자가 가장 많이 헷갈리는 부분이므로 화면에 띄워 함께 읽는다.

```text
  {
<<<<<<< HEAD
    "name": "강사 (충돌 드릴)",
    ...
    "github": "drill-instructor"
=======
    "name": "홍길동",
    ...
    "github": "내아이디"
>>>>>>> 1a2b3c4 (feat: 팀 카드에 홍길동 추가)
  }
]
```

- `<<<<<<< HEAD`부터 `=======`까지는 리베이스 대상인 main 쪽 내용이다. 리베이스 중에는 HEAD가 main이라는 점을 짚어 준다.
- `=======`부터 `>>>>>>>`까지는 학습자 자신의 커밋 내용이다.
- 해결은 두 카드를 모두 남기고, 표시 줄 세 개를 지우고, 두 카드 사이에 `},`와 `{`를 넣는 것이다.

## 예상되는 실수와 대처

| 실수 | 증상 | 대처 |
|---|---|---|
| 한쪽 카드만 남김 | 검사는 통과하지만 카드가 사라짐 | 리뷰에서 카드 개수를 확인시킨다 |
| 표시 줄을 남김 | check 실패: "병합 충돌 표시가 남아 있습니다" | 행 번호를 보고 지운다 |
| 쉼표 누락 또는 초과 | check 실패: "JSON 문법 오류입니다. N행 M열 근처" | 메시지의 행을 연다 |
| `git push`만 실행 | `rejected (non-fast-forward)` | `git push --force-with-lease` |
| `git pull`로 병합 커밋 생성 | PR에 병합 커밋이 섞임 | Squash 병합이므로 그대로 진행해도 된다 |
| 리베이스 중 다른 파일까지 수정 | 디프가 커짐 | `git rebase --abort` 후 다시 시작 |

## 복구 방법

**리베이스를 처음부터 다시 하고 싶을 때**

```bash
git rebase --abort
git status
```

Orca에서는 Source Control(소스 제어)의 Abort rebase(리베이스 중단)를 누른다. 브랜치는 리베이스 시작 전 상태로 돌아간다.

**이미 잘못 해결하고 푸시했을 때**

```bash
git reflog                                   # 리베이스 전 커밋(예: HEAD@{3}) 찾기
git reset --hard HEAD@{3}                    # 그 시점으로 되돌리기
git fetch origin && git rebase origin/main   # 다시 해결
git push --force-with-lease
```

**강사 카드를 지워야 할 때**

드릴을 다시 하려면 강사 카드를 지우는 PR을 만들어 병합한다. 같은 저장소에서 두 번째 드릴을 할 때는 `DRILL_GITHUB` 값을 바꾸어 아이디 중복을 피한다.

## 마무리 질문

1. 충돌이 난 이유는 무엇인가. 같은 파일의 같은 위치를 두 사람이 바꾸었기 때문이다.
2. 섹션 구현(실습 2)에서는 왜 충돌이 없었는가. 역할마다 파일이 나뉘어 있었기 때문이다.
3. `--force`와 `--force-with-lease`는 무엇이 다른가. 후자는 원격 브랜치가 내가 마지막으로 본 상태일 때만 덮어쓴다.
