# 실습 가이드

3시간 워크숍 "GitHub 팀 바이브코딩: Orca와 gh CLI로 4~5인 협업"의 학습자용 안내서다. 실습은 네 개이며, 명령은 위에서부터 그대로 따라 입력하면 된다.

| 실습 | 내용 | 시간 |
|---|---|---|
| 1 | 환경 준비: gh, Orca, 팀 저장소 | 30분 |
| 2 | 구현: 이슈에서 워크트리, 에이전트, PR까지 | 35분 |
| 3 | 리뷰: PR 확인, 의견, 승인, 병합 | 30분 |
| 4 | 충돌: team.json 충돌 해결과 강제 푸시 | 25분 |

**표기 안내**

- `<팀저장소>`는 강사가 알려 준 `owner/name`(예: `takjakim/team1-hub`)으로, `<번호>`는 이슈나 PR 번호로 바꾼다.
- Orca 화면 문구는 Orca 1.4 기준 영문이며, 한국어 화면에서는 괄호 안 문구로 보인다. 버전에 따라 위치나 이름이 조금 다를 수 있다.
- Windows에서는 PowerShell 또는 Git Bash를 쓴다. `python3`가 없으면 `python`을 쓴다.

## 실습 1. 환경 준비

### 1-1. GitHub CLI 설치

```bash
# macOS
brew install gh

# Windows (PowerShell)
winget install --id GitHub.cli
```

설치 후 터미널을 새로 열고 버전을 확인한다.

```bash
gh --version
```

### 1-2. GitHub 로그인

```bash
gh auth login
```

질문에는 차례대로 `GitHub.com`, `HTTPS`, Git 인증 사용 `Yes`, `Login with a web browser`를 고른다. 화면의 일회용 코드를 브라우저에 입력하면 끝난다.

```bash
gh auth status        # Logged in to github.com account <내아이디> 가 보이면 성공
```

### 1-3. Git과 Node 확인

```bash
git --version
node --version        # v20.19 이상. v22 LTS를 권장한다
git config --global user.name "홍길동"
git config --global user.email "내-깃허브-메일@example.com"
```

Node가 없으면 macOS는 `brew install node`, Windows는 `winget install OpenJS.NodeJS.LTS`로 설치한다.

### 1-4. Orca 설치

```bash
# macOS
brew install --cask stablyai/orca/orca
```

Windows는 https://github.com/stablyai/orca/releases 에서 `orca-windows-setup.exe`를 내려받아 실행한다.

### 1-5. Orca CLI 등록

1. Orca를 실행한다.
2. Settings(설정) → General(일반) → Orca CLI 항목에서 CLI 명령을 등록한다.
3. 터미널을 새로 열고 확인한다.

```bash
orca status
```

### 1-6. 팀 저장소 받기

강사가 보낸 GitHub 초대 메일을 수락한 뒤 저장소를 복제하고 검사를 한 번 실행한다.

```bash
gh repo clone <팀저장소>
cd <저장소이름>
node scripts/check.mjs        # "모든 검사를 통과했습니다." 가 나오면 성공
```

Orca 왼쪽 사이드바의 프로젝트 영역에서 `+` → Add Project(프로젝트 추가)를 누르고 방금 복제한 폴더를 고른다. 터미널에서는 다음과 같이 추가할 수도 있다.

```bash
orca repo add --path .
```

**체크포인트**: `gh auth status`, `orca status`, `node scripts/check.mjs`가 모두 정상이고, Orca 사이드바에 팀 저장소가 보인다.

## 실습 2. 구현: 이슈에서 PR까지

### 2-1. 이슈 고르기

```bash
gh issue list                         # 역할별 이슈 #1~#5와 드릴 이슈 #6
gh issue view 2                       # 자기 역할 이슈의 담당 파일과 완료 기준 확인
gh issue edit 2 --add-assignee @me    # 이슈를 자기에게 할당
```

역할과 담당 파일은 `docs/역할카드.md`에 정리되어 있다. 아래 예시는 역할 B(이슈 #2, 할 일 보드) 기준이다.

### 2-2. 워크트리 만들기 (Orca)

1. 사이드바에서 팀 저장소 옆 `+` 또는 Create Workspace(워크스페이스 생성)를 누른다.
2. Workspace name(워크스페이스 이름)에 작업 이름을 적는다. 예: `feat-2-todo-board`
3. Create From(다음에서 만들기)은 `origin/main`으로 둔다.
4. Agent(에이전트)는 Claude Code를 고른다.
5. GitHub 이슈 #2를 연결한다.
6. 만들기를 누르면 `orca.yaml`의 setup 명령(`node scripts/check.mjs`)이 먼저 실행되고, 새 워크트리에서 Claude Code가 열린다.

브랜치 이름은 `feat/<이슈번호>-<짧은설명>` 규칙을 따른다. 만들어진 브랜치 이름이 다르면 워크트리 터미널에서 바꾼다.

```bash
git branch --show-current
git branch -m feat/2-todo-board
```

**CLI 대안**: 저장소 폴더에서 다음을 실행해도 같은 결과를 얻는다.

```bash
gh issue list
orca worktree create --name feat-2-todo-board --agent claude --issue 2 --base-branch origin/main \
  --prompt "이슈 #2를 구현해 주세요. src/sections/board.js만 수정하고, 끝나면 node scripts/check.mjs를 실행해 주세요."
```

### 2-3. 에이전트에게 구현 요청

Claude Code는 저장소의 `CLAUDE.md`(Codex는 `AGENTS.md`)를 자동으로 읽으므로 수정 범위와 코드 규칙을 이미 알고 있다. 프롬프트에는 이슈 번호, 담당 파일, 완료 기준, 검사 명령을 넣는다.

```text
이슈 #2를 구현해 주세요. src/sections/board.js만 수정합니다.
먼저 구현 계획을 3줄로 보여 주고, 제가 확인하면 코드를 작성해 주세요.
완료 기준은 gh issue view 2 로 확인할 수 있습니다.
끝나면 node scripts/check.mjs를 실행해 통과를 확인해 주세요.
```

역할별 상세 프롬프트 예시는 `docs/역할카드.md`에 있다.

### 2-4. 검사와 화면 확인

```bash
node scripts/check.mjs
python3 -m http.server 8000     # 브라우저에서 http://localhost:8000
```

워크트리마다 폴더가 다르므로 서버는 작업 중인 워크트리에서 실행한다. 포트가 사용 중이면 `8001`처럼 다른 번호를 쓴다. `index.html`을 더블클릭해서 열면 ES 모듈이 막혀 화면이 비므로 반드시 로컬 서버로 연다.

### 2-5. 커밋, 푸시, PR (Orca Source Control)

오른쪽 사이드바의 Source Control(소스 제어)에서 진행한다.

1. Stage All(모두 스테이지)로 변경 파일을 올린다. 담당 파일만 있는지 확인한다.
2. Generate with AI(AI로 생성)로 커밋 메시지를 만든다. `feat: 할 일 보드 추가, 완료, 삭제 구현`처럼 `type: 요약` 형식인지 확인하고 고친다.
3. Commit(커밋)을 누른다.
4. Push(푸시)를 누른다.
5. Create PR(PR 작성)을 누르고 본문에 다음 두 줄을 넣는다.

```text
Closes #2
에이전트: Claude Code
```

**CLI 대안**

```bash
git status
git add src/sections/board.js
git commit -m "feat: 할 일 보드 추가, 완료, 삭제 구현"
git push -u origin HEAD
gh pr create --fill                                  # 커밋 메시지로 제목과 본문 작성
gh pr edit --body "$(printf 'Closes #2\n에이전트: Claude Code')"
```

### 2-6. CI 확인

```bash
gh pr checks --watch            # check 가 pass 가 될 때까지 기다린다
```

실패하면 `gh pr checks`의 링크에서 로그를 열고, 로컬에서 `node scripts/check.mjs`로 같은 오류를 재현해 고친 뒤 다시 푸시한다.

**체크포인트**: 자기 PR이 열려 있고, 본문에 `Closes #번호`가 있으며, check가 통과했다.

## 실습 3. 리뷰와 병합

리뷰는 A가 B를, B가 C를, C가 D를, D가 E를, E가 A를 보는 순서로 돌아가며 맡는다. 네 명 팀이면 E를 건너뛴다(E는 강사가 맡는다).

### 3-1. 리뷰할 PR 찾기

```bash
gh pr list
gh pr view <번호>               # 본문과 확인 사항
gh pr diff <번호>               # 변경 내용
```

### 3-2. 로컬에서 직접 확인

```bash
gh pr checkout <번호>
node scripts/check.mjs
python3 -m http.server 8000
```

Orca에서는 PR 화면의 Start workspace from PR(PR에서 워크스페이스 시작)로 PR 브랜치의 워크트리를 만들 수 있다. 자기 작업 워크트리를 건드리지 않고 리뷰할 수 있어 편리하다.

### 3-3. 의견 남기기

리뷰어는 GitHub PR 화면의 Files changed에서 줄 단위 의견을 남기거나 CLI를 쓴다.

```bash
gh pr review <번호> --comment -b "제안: 빈 입력일 때 버튼을 비활성화하면 좋겠습니다."
gh pr review <번호> --request-changes -b "공용 파일 base.css가 바뀌었습니다. 되돌려 주십시오."
```

PR 작성자는 자기 워크트리의 디프 뷰어에서 고칠 줄에 주석을 달고 Send Review Notes를 눌러 Send notes to 메뉴에서 에이전트를 골라 전달한다. 에이전트가 고치면 검사 후 다시 커밋하고 푸시한다. 같은 PR에 커밋이 추가되므로 새 PR을 만들 필요가 없다.

### 3-4. 승인

```bash
gh pr review <번호> --approve -b "완료 기준을 확인했습니다."
```

### 3-5. 병합

승인 1명과 check 통과가 모두 갖춰지면 PR 작성자가 병합한다. 병합 방식은 Squash and merge다.

```bash
gh pr checks <번호>
gh pr merge <번호> --squash --delete-branch
```

웹에서는 PR 하단의 Squash and merge 버튼을 쓴다. 병합되면 `Closes`로 연결한 이슈가 자동으로 닫힌다.

### 3-6. 최신 main 받기

다른 사람의 PR이 병합되면 자기 브랜치를 최신 main 위로 옮긴다. 각자 다른 파일을 고쳤으므로 충돌 없이 끝난다.

```bash
git fetch origin
git rebase origin/main
```

**체크포인트**: 팀의 섹션 PR이 모두 병합되었고, GitHub Pages 주소에서 다섯 섹션이 보인다. 주소는 보통 `https://<owner>.github.io/<저장소이름>/`이며, 다음 명령으로 정확한 주소를 확인한다.

```bash
gh api repos/<팀저장소>/pages -q .html_url
```

## 실습 4. 충돌 해결

모두가 같은 파일의 같은 위치를 고치면 충돌이 생긴다. 충돌은 사고가 아니라 Git이 두 변경 중 무엇을 남길지 사람에게 묻는 절차다.

### 4-1. 자기 카드 추가 PR 만들기 (드릴 이슈 #6)

`origin/main`에서 새 워크트리를 만든다. 작업 이름 예: `feat-6-card-<내아이디>`, 브랜치 이름: `feat/6-card-<내아이디>`.

`src/data/team.json` 배열 끝에 자기 카드를 추가한다. 바로 앞 카드의 `}` 뒤에 쉼표를 붙인다.

```json
  {
    "name": "홍길동",
    "role": "역할 B",
    "focus": "할 일 보드",
    "github": "내아이디"
  }
```

```bash
node scripts/check.mjs
git add src/data/team.json
git commit -m "feat: 팀 카드에 홍길동 추가"
git push -u origin HEAD
gh pr create --fill
gh pr edit --body "$(printf 'Refs #6\n에이전트: 직접 작성')"
```

강사의 신호가 있을 때까지 병합하지 않는다.

### 4-2. 강사가 main을 바꾼다

강사가 `scripts/conflict-drill.sh`로 main의 `team.json` 배열 끝에 "강사 (충돌 드릴)" 카드를 추가한다. 이제 모든 팀원의 PR에 "This branch has conflicts" 표시가 생긴다.

### 4-3. 최신 main을 받아 충돌 확인

```bash
git fetch origin
git rebase origin/main
```

Orca에서는 Source Control(소스 제어)의 Pull(풀) 또는 리베이스 작업 후 Review conflicts(충돌 리뷰)를 누르면 충돌 파일이 열린다.

### 4-4. 충돌 해결

충돌 부분은 대략 다음과 같이 보인다. Git이 두 카드의 공통 줄(`{`, `}`)을 하나로 합쳐 버려서 카드 내용만 위아래로 갈라져 있다.

```text
  {
<<<<<<< HEAD
    "name": "강사 (충돌 드릴)",
    "role": "강사",
    "focus": "충돌 드릴용 카드입니다. 해결할 때 이 카드와 자기 카드를 모두 남깁니다.",
    "github": "drill-instructor"
=======
    "name": "홍길동",
    "role": "역할 B",
    "focus": "할 일 보드",
    "github": "내아이디"
>>>>>>> 1a2b3c4 (feat: 팀 카드에 홍길동 추가)
  }
]
```

두 카드를 모두 남기고, 표시 줄 세 개(`<<<<<<<`, `=======`, `>>>>>>>`)를 지우고, 카드 사이에 `},` 와 `{`를 넣는다.

```json
  {
    "name": "강사 (충돌 드릴)",
    "role": "강사",
    "focus": "충돌 드릴용 카드입니다. 해결할 때 이 카드와 자기 카드를 모두 남깁니다.",
    "github": "drill-instructor"
  },
  {
    "name": "홍길동",
    "role": "역할 B",
    "focus": "할 일 보드",
    "github": "내아이디"
  }
]
```

Orca의 Resolve with AI(AI로 해결)를 쓰면 에이전트가 같은 작업을 제안한다. 결과를 반드시 직접 읽고 두 카드가 모두 남았는지 확인한다.

```bash
node scripts/check.mjs                  # 충돌 표시가 남았거나 쉼표가 틀리면 행 번호와 함께 실패한다
git add src/data/team.json
GIT_EDITOR=true git rebase --continue   # 커밋 메시지는 그대로 두고 리베이스를 마친다
```

Windows PowerShell에서는 `git -c core.editor=true rebase --continue`를 쓴다.

### 4-5. 강제 푸시(with lease)

리베이스로 커밋이 새로 만들어졌으므로 일반 푸시는 거부된다. 다른 사람이 그 사이 같은 브랜치에 푸시했으면 덮어쓰지 않도록 `--force-with-lease`를 쓴다.

```bash
git push --force-with-lease
```

Orca에서는 Source Control(소스 제어)의 Force Push(강제 푸시)를 누른다. 이 버튼은 with lease 방식으로 동작한다.

### 4-6. 차례로 병합

강사의 안내에 따라 한 사람씩 병합한다. 앞사람의 카드가 병합되면 뒷사람의 PR에는 다시 충돌이 생기므로 4-3부터 4-5를 반복한다. 모두 끝나면 강사가 드릴 이슈 #6을 닫는다.

### 4-7. 막혔을 때 되돌리기

```bash
git rebase --abort      # 리베이스 시작 전 상태로 돌아간다
git status              # 작업 트리가 깨끗한지 확인
```

Orca에서는 Source Control(소스 제어)의 Abort rebase(리베이스 중단)를 누른다. 되돌린 뒤 4-3부터 다시 시도한다.

**체크포인트**: 팀원 모두의 카드와 강사 카드가 main의 `team.json`에 있고, check와 Pages 배포가 통과했다.

## 자주 겪는 문제

| 증상 | 원인 | 해결 |
|---|---|---|
| 화면이 "페이지를 불러오는 중입니다"에서 멈춤 | `index.html`을 파일로 직접 열었다 | `python3 -m http.server 8000` 후 http://localhost:8000 |
| 섹션 하나만 빨간 오류 문구 | 그 섹션의 render에서 예외가 났다 | 브라우저 개발자 도구 콘솔의 `[섹션id]` 로그 확인 |
| `git push`가 main에서 거부됨 | main은 보호되어 직접 푸시할 수 없다 | 브랜치를 만들어 PR로 올린다 |
| 리베이스 후 `git push`가 거부됨 | 커밋 기록이 바뀌었다 | `git push --force-with-lease` |
| PR에 Merge 버튼이 비활성화 | 승인 또는 check가 부족하다 | 리뷰 요청, `gh pr checks`로 실패 원인 확인 |
| check가 "index.js 목록에 없는 섹션 파일" | `src/sections/`에 새 파일을 만들었다 | 코드를 자기 섹션 파일 안으로 옮긴다 |
